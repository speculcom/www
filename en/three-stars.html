Three stars, one door: complete one game step by step

This site-authored browser game asks you to collect three stars and reach E. Explore its loop, pause, saves, touch controls, resizing and publication. Code checks concern this example only, not engines or AI products.

What this is: a browser game written for this site with a six-stage teaching sequence. The same sample gains pause, versioned saves, touch controls, resizing and release checks — the code and the prose change together.

Scope of the checks: the section "What this site checked" covers this sample and this package only. It is not an engine evaluation and not an AI-product evaluation, and it supports no pass-rate or accuracy claim.

Where the data goes: no account, no backend, no network call. Saves go only to your own browser (key specul-three-stars-v1) and the exported JSON stays on your machine. Every example value on this page is fictional.

Related pages: the core loop · saves and offline behaviour · export and ship · the AI asset ledger

Stage 1 · Establish the core loop

What changes here: Keep level, position, collected stars and moves separate. Arrows/WASD update state before repainting. Walls do not add moves; reaching the exit completes the game only after collecting all stars.

Where the code sits

state = { x: 1, y: 1, moves: 0, collected: [] };
// Input -> legal move -> update state -> render
// Completion is derived from position and collected stars.

How to check it actually holds

  • Move left into a wall: position and moves stay unchanged. Count each star once. Reaching E before collecting all stars does not complete the game.

Where to look when it does not

  • For out-of-bounds moves, duplicate stars or wall moves being counted, inspect coordinates, legal moves and update order. Do not treat UI text as the state store.

→ Next stage: Pause and restart

Stage 2 · Pause and restart

What changes here: Pause is independent of level/progress. A hidden page pauses; returning requires explicit resume. Restart resets the board without deleting a browser save.

Where the code sits

if (paused) return;
// On visibilitychange: if document.hidden, pause.
// Restart creates a fresh state; it does not call localStorage.clear().

How to check it actually holds

  • Moves stay unchanged while paused and work after resume. A hidden/returned page remains paused. Restart restores the initial position and zero stars.

Where to look when it does not

  • If movement bypasses pause, route every input through one guard. If restart deletes saves, separate current-board reset from deleting this project’s saved data.

→ Next stage: Versioned saves and fallback

Stage 3 · Versioned saves and fallback

What changes here: Save only level ID, schema version, coordinates, moves and collected items. Validate fields, position and level; derive completion rather than trusting a flag. Storage-blocked play still works with JSON download/import. Saves are not uploaded.

Where the code sits

{ schema: 1, level: 'three-stars-1', x, y, moves, collected }
// Parse -> validate -> replace state. Invalid saves keep the current board.
// Browser save and file import are separate explicit actions.

How to check it actually holds

  • Save after moving, reload the page and load to restore position/stars. Export/import should agree. Reject wrong versions, wall positions, duplicate stars and oversized files while preserving the board.

Where to look when it does not

  • localStorage depends on origin and browser policy; file:// behavior is not guaranteed. Retain an unreadable file rather than clearing all browser storage. This example accepts version 1 only and does not pretend to migrate it.

→ Next stage: Share movement between touch and keyboard

Stage 4 · Share movement between touch and keyboard

What changes here: Directional buttons call the same move function as keyboard input. Keep usable targets/focus. Capture arrows only while the board has focus; do not block page scrolling or zooming.

Where the code sits

button.addEventListener('click', () => move(dx, dy));
// Direction buttons: touch-action: manipulation.
// Keyboard handling belongs to the focusable board, not the whole document.

How to check it actually holds

  • The same route through buttons/arrows yields the same state. Both honor pause. Tab enters/exits the board and controls without a focus trap.

Where to look when it does not

  • For touch-only wall/pause bypasses, inspect the shared move path. For lost zooming, check whole-page touch-action:none or unconditional event prevention.

→ Next stage: Resize the view without resetting state

Stage 5 · Resize the view without resetting state

What changes here: Use seven flexible columns within the container. Store coordinates in state, not screen pixels. The narrow-board option is a display exercise; every stage retains basic narrow-screen usability.

Where the code sits

grid-template-columns: repeat(7, minmax(0, 1fr));
// Layout changes do not recreate initial game state.
// Saved coordinates remain grid coordinates.

How to check it actually holds

  • After moving, switch board width or resize/orient the window without losing position, stars or moves. Check 320px widths, long English text and controls, not only the presence of a scrollbar.

Where to look when it does not

  • If resize restarts play, inspect state resets in layout handlers. If loads shift cells, distinguish pixel and grid coordinates.

→ Next stage: Package, replay and check publication

Stage 6 · Package, replay and check publication

What changes here: The download includes HTML, scripts, styles, brand assets, an asset ledger and hashes. The game itself has no network calls/backend; site/document links need connectivity. For your own publication, check code/asset rights, paths/case, HTTPS and target browsers.

Where the code sits

index.html + game.js + game.css + brand.js + brand.css
asset-ledger.json + manifest.json + README.txt + NOTICE.txt
// Extract, serve on localhost, then test the actual packaged files.

How to check it actually holds

  • Play the extracted package, then check pause, saves, blocked storage, keyboard and touch. Inspect the ledger and every published file; one successful page load is not a complete release check.

Where to look when it does not

  • For missing files, check case and relative paths. For lost saves, check origin/protocol and browser policy. The sample download grants no separate redistribution licence; check site terms before republishing copied content.

What this site checked · and did not

Verified on 2026-11-06, scoped to this sample and this package only; every line below was run in a browser, not merely read off the code.

  • Collected all three stars from the start and reached the exit with matching position, star count, moves and completion; a wall move adds none.
  • Invalid imports rejected: a wrong schema version, a wall coordinate, duplicate stars and an oversized file each leave the board unchanged.
  • Play stays complete when browser storage is denied, with the download/import route offered instead.
  • Keyboard and on-screen buttons share one move path; neither moves while paused; Tab enters and leaves the board and the controls.
  • A 320px narrow screen, taps, both themes and both languages pass; resizing the window or switching board width keeps the state.
  • With scripting off the six stages stay fully readable — the teaching text is static HTML inlined at build time, not injected by JS.
  • The package: extracted with an independent tool, compared byte-for-byte against its sources, CRC-checked, and opened offline without a server.

Not covered: other browsers and real devices, storage policy on other origins or protocols, how the feel holds up over a long session, and any judgement of an engine or an AI product. This site runs no benchmarks and publishes no pass rate or accuracy figure.

What this sample does not claim

  • It proves nothing about an engine or an AI product; it describes this 7×5 sample’s own code behaviour
