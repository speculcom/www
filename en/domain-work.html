Field guide · Work & business workflows

Office and business workflows: split a job into steps AI can take

You ask AI to “handle the invoices” and get a smooth paragraph with unchecked amounts, tax IDs and company names. Office work is not a faster chat box; it is a checkable pipeline: where input comes from, who does which step, what a human must see and where failures go back. Split the job, and AI has a place.

For Anyone handing documents, spreadsheets, meetings or repetitive work to AI You leave with A process breakdown, a human-review checklist and a one-week pilot path Time 10 minutes to read; about half a day to break down one process Last checked 25 Nov 2026

This page gives a workflow and acceptance framework, not legal, financial or HR advice. Contracts, invoices and personal data follow your organisation’s rules and local law.

If you only have five minutes
  1. Write the input, output, definition of done and return conditions first.
  2. Let AI draft and move data; a human checks critical numbers and names.
  3. Run one week of real work before rolling it out to a department.

The full guide starts below. Use the tables for reference; you do not need to memorise them.

One concrete job

Take one concrete job: 50 invoices a day. AI only extracts amount, tax ID and company name into a sheet; finance checks 10. Run that for a week.

Start with a reversible extraction task, not fully automated approvals. Scale only after rollback and sample review exist.

1 · Draw the pipeline before choosing a tool

A one-page pipeline card states five things: what the input is (document, audio, table), where the output lands (system and fields), who owns the result, what counts as acceptance, and which queue receives failures or low-confidence cases. Without these five, any model only hides uncertainty deeper.

Separate assistance from automation: assistance proposes and a human decides; automation writes or sends directly. Assistance can launch earlier; automation needs permissions, audit and rollback. Do not use one pilot to prove both.

Mark where a human waits for the model and where the model waits for a human. The first is review; the second is missing input. Their cost and metrics are different.

2 · Four high-frequency tasks; start with one

Document extraction: scan/PDF → table fields. The key is not OCR accuracy but field definitions, page and coordinates, unknown values and a review queue. The same invoice moves fields across supplier templates; a generic model concentrates errors on a minority of templates.

Meeting notes: audio → minutes and actions. Separate verbatim speech, summary, decision and action. Keep speaker, timestamp and the original sentence so claims can be checked. A smooth summary does not replace confirmation of key decisions.

Table merge/reconciliation: several tables → one master table plus an exception list. Define the key, duplicate rules and conflict priority first. Do not let a model merge “because it looks similar”. For amounts, dates and IDs, a rule engine is usually more reliable than a model.

Document review: long text → issue table. Every issue needs a source location, suggested change and severity. An issue without a location cannot be checked. Contracts, compliance and HR documents need a qualified final reviewer.

Selection advice: start with extraction that is structured, sampleable and reversible. Put approvals, external sending and payments — irreversible actions — later.

3 · Structured output: give “unknown” a place to live

An output schema fixes three things: field names and types, required vs optional, and how unknown, conflicting or not-applicable values are represented. A binary yes/no forces “not found” into a guess; allowing null with a reason keeps the error visible.

Each result should carry provenance where possible: page, cell, timestamp or source snippet. Provenance is not decoration; it is the entry point for review, correction and audit. A field without provenance should be treated as a candidate, not a fact.

Confidence is a routing signal, not an accuracy guarantee. A model saying “0.95” does not mean 95% correct. Measure the real error rate of high- and low-confidence groups on a fixed sample, then set the threshold.

4 · The human role: review is not clicking “approve”

A review screen should show source, extracted result, provenance, rule warnings and edit history in one view. A result plus an approve button degrades review into a rubber stamp.

Tier by risk: low-risk fields can be sample-reviewed; amounts, dates, identity, permissions and external commitments need row-by-row or four-eyes review. Log who may edit, what changed and why — not only the final value.

Give reviewers exits: reject, return for missing material, escalate to an expert. Only approve/reject piles exceptions into one queue and invites rushed handling.

5 · Permissions and data: access to a file does not mean access to every file

Least privilege applies to three identities: the person, the agent and the connector. Which folders can it read, which systems can it write, which external APIs can it call, where can data go? Running every workflow under one shared admin account means there is no boundary.

Draw the data flow: where input comes from, which model or connector it passes, where logs land, how long they stay, who can export and how deletion is verified. “Local deployment” alone does not answer these; local systems can still call external APIs, send telemetry or keep backups.

The most missed office context is other people: email signatures, meeting audio, spreadsheet comments and shared-drive paths can contain personal data. Classify input (public/internal/confidential/personal) before deciding whether it may enter an external model.

6 · Cost: include human minutes and rework

The total cost of an office task includes model calls, retries, storage, licence seats, review minutes, rework and delay. Comparing only price per million tokens produces a false “cheaper is better” conclusion.

Use a recomputable formula: cost per accepted item = (calls + retries + storage + licences) / accepted items + review minutes × labour rate + rework cost. The denominator counts accepted items, not model responses.

The scale-up threshold is not a cheaper model; it is an exception rate that review capacity can absorb. If exceptions do not fall, automation moves work from execution to rework.

7 · Acceptance: fix the sample before talking about launch

Prepare a fixed set of 20–30 items (real, redacted or fictional) covering common templates, edge formats and known exceptions. Run the human baseline first, recording time, error types and rework; then run the AI pipeline on the same set.

At least four acceptance metrics: first-pass yield, field-level error rate, exception detection rate and human minutes per item. Add two safety metrics: unauthorised access attempts and fields without provenance. Without a baseline, do not claim an improvement.

Launch with a shadow run: AI output does not write to the live system at first; run it alongside human output, explain every difference, then switch. Keep a rollback switch and the old process for at least one billing cycle.

Rule of thumb: if a workflow cannot answer “how will we detect an error, who fixes it and how do we roll back”, it is not ready to launch.

8 · A minimum path to deployment

  • Pick one task, one input format and one output system; do not launch several at once.
  • Write the schema and exception rules: fields, types, unknown, conflict and source location.
  • Prepare 20–30 fixed samples and run the human baseline first.
  • Build a replayable pipeline: input, model, rules, review and write all logged.
  • Run in shadow mode and explain every AI-versus-human difference.
  • Review by risk tier and provide reject, return-for-input and escalate exits.
  • Recalculate cost and exception rate on the fixed sample; switch to live writes only after thresholds are met.
  • Regression on change: a new template, model, rule or permission triggers the sample again.
