领域深度 · 智能体Field guide · Agents

智能体：先把它当一条有权限的流程Agents: treat it as a permissioned process first

智能体不是「会自己干活的聊天框」。它由模型、工具、状态、控制循环和权限边界组成。演示里跑通一次，不代表能上线；上线要能回放、能限权、能停、能评测。先做一条单任务、可审批、可回放的流程，再谈多智能体。An agent is not a chat box that does work by itself. It is a system of model, tools, state, control loop and permission boundaries. One successful demo does not mean it is ready to ship; shipping requires replay, least privilege, a stop button and evaluation. Build one single-task, approvable, replayable process before discussing multi-agent systems.

本页是 Specul 的智能体判断框架，不是框架或产品的排名。工具能力、许可与安全边界以所链页面和原始来源为准。This is Specul’s decision framework for agents, not a ranking of frameworks or products. Tool capabilities, licences and safety boundaries remain with the linked pages and original sources.

先做单任务、可回放、可审批的 Agent；多 Agent 是复杂度，不是能力证明。Build a single-task, replayable, approvable agent first. Multi-agent is complexity, not proof of capability.

1 · 五个部件：模型、工具、状态、循环、权限1 · Five parts: model, tools, state, loop, permissions

模型负责提出下一步，工具负责改变外部世界，状态负责记住之前发生了什么，控制循环负责在合适的时候继续或停止，权限负责决定哪些动作根本不能做。五者缺一，智能体就会退化成「会调用函数的聊天」。The model proposes the next step, tools change the outside world, state remembers what happened, the control loop decides whether to continue or stop, and permissions decide which actions are forbidden. Remove one and the agent collapses into a chatbot that calls functions.

最容易被忽略的是权限。模型可以「想」做任何事，但系统只能让它「做」被明确授权的动作。把权限写在提示词里不算权限；权限必须由运行时代码、身份系统或审批流程执行。Permissions are the most overlooked part. A model may think about anything, but the system may only let it do explicitly authorised actions. Writing permissions in a prompt is not permission; they must be enforced by runtime code, an identity system or an approval flow.

2 · 任务边界：一件事、一个负责人、一个完成定义2 · Task boundary: one job, one owner, one definition of done

一个可上线的智能体，任务应该能用一句话说清：它读什么、做什么、产出什么、什么情况下停。任务越宽，越难判断它有没有做完，也越难限制它的副作用。A shippable agent should have a task describable in one sentence: what it reads, what it does, what it produces and when it stops. The broader the task, the harder it is to know whether it is done and to limit side effects.

每个任务要有一个人类负责人。负责人不是「出了问题再找的人」，而是事先定义完成标准、审批不可逆动作、决定什么时候停的人。没有负责人的智能体，出事时只会互相指认。Every task needs a human owner. The owner is not the person you call after something breaks; they define done criteria in advance, approve irreversible actions and decide when to stop. An agent without an owner produces blame, not accountability.

不可逆动作要单独列出：对外发送、付款、删除、发布、改权限、动生产数据。对这些动作，默认要人工确认；如果确实要自动执行，必须有额度、白名单、回滚和审计。List irreversible actions separately: sending externally, paying, deleting, publishing, changing permissions, touching production data. By default these require human confirmation. If they must be automated, they need limits, allowlists, rollback and audit.

判断句：如果一件事做完没有可观察的结果，也没有人能为结果负责，它还不适合交给智能体。Rule of thumb: if the work has no observable result and no one accountable for it, it is not ready for an agent.

3 · 工具与权限：能调用不等于该调用3 · Tools and permissions: can call does not mean should call

工具定义越模糊，模型越容易乱填参数。每个工具要写清：做什么、输入是什么、输出是什么、失败返回什么、是否幂等、是否会产生副作用。最好让工具在参数不合法时直接拒绝，而不是「猜一个」继续。The vaguer the tool definition, the more likely the model fills in wrong arguments. Each tool should state what it does, its input, its output, its failure return, whether it is idempotent and whether it has side effects. Tools should reject invalid arguments instead of guessing and continuing.

权限要按「身份 × 动作 × 对象 × 范围」授予。同一个智能体，读知识库和发外部邮件应该是两种权限；读一个项目和读所有项目也应该是两种权限。把工具权限收窄，比在提示词里写「不要乱来」有效得多。Grant permissions by identity × action × object × scope. For the same agent, reading a knowledge base and sending external email are different permissions; reading one project and reading all projects are different too. Narrow tool permissions is far more effective than writing “do not misbehave” in a prompt.

MCP、插件和第三方工具还是供应链。固定版本、核对来源、限制网络与文件访问、保留清单，和装一个依赖没有本质区别。工具越多，攻击面越大；先接一个真正需要的工具，比接十个「以后可能用得上」的更安全。MCP servers, plugins and third-party tools are also supply chain. Pin versions, verify sources, limit network and file access, keep an inventory — it is no different from adding a dependency. More tools mean more attack surface. Connect one tool you truly need before ten you might need later.

4 · 状态与记忆：先能回放，再谈长期记忆4 · State and memory: replay first, long-term memory later

状态不是「把聊天记录全塞进上下文」。至少要区分：本次任务的临时状态、跨任务的长期记忆、外部系统的真实状态。三者混在一起，智能体会把旧结论当现在，把猜出来的东西当事实。State is not stuffing the whole chat history into context. Separate at least: temporary state for this task, long-term memory across tasks, and the real state of external systems. Mix them and the agent treats old conclusions as current and guesses as facts.

先做可回放：记录每一步的输入、模型输出、工具调用、工具返回、审批和最终结果。回放不是为了「看日志」，而是为了在失败时判断是哪一步错了，以及能不能用同一输入复现。没有回放，评测和审计都无从谈起。Build replay first: record each step’s input, model output, tool call, tool return, approval and final result. Replay is not for “looking at logs”; it is for identifying which step failed and whether the same input reproduces. Without replay, evaluation and audit are impossible.

长期记忆要有写入规则、过期规则和删除规则。什么值得记、记多久、谁能读、如何纠错，都要在写入前想清楚。把所有对话永久向量化，既贵又容易把错误固化。Long-term memory needs write rules, expiry rules and deletion rules. Decide what is worth remembering, for how long, who can read it and how to correct it before writing. Permanently vectorising every conversation is expensive and freezes mistakes.

5 · 控制循环：继续、重试、停止都要有上限5 · Control loop: continuing, retrying and stopping all need limits

一个健康的循环至少有四道闸：最大步数、最大时长、最大成本、最大重试次数。没有上限的循环，会在工具反复失败时不断重试，或在模型反复「再确认一下」时烧掉预算。A healthy loop has at least four gates: maximum steps, maximum duration, maximum cost and maximum retries. Without limits, a loop keeps retrying when a tool fails repeatedly, or burns budget while the model “checks once more”.

重试要区分可重试和不可重试。网络超时可以重试；参数错误、权限拒绝、对象不存在通常不该重试。写操作还要幂等：同一个动作重复执行，不能产生两封邮件、两笔付款或两条记录。Distinguish retryable from non-retryable failures. Network timeouts can be retried; invalid arguments, permission denials and missing objects usually should not. Write actions must be idempotent: repeating the same action must not create two emails, two payments or two records.

停止条件要显式：任务完成、达到上限、需要人工审批、出现安全违规、或证据不足。最危险的不是「不会做」，而是「不知道已经该停」。Stop conditions must be explicit: task done, limit reached, human approval needed, safety violation, or insufficient evidence. The most dangerous state is not “cannot do it” but “does not know it should stop”.

6 · 评测：看任务、轨迹、工具和安全，不只看最终一句话6 · Evaluation: task, trajectory, tools and safety, not just the final sentence

智能体的评测不能只看最终答案。至少要记录：任务是否完成、步骤是否合理、工具调用是否正确、是否越权、成本多少、失败时是否安全退出。一个答案看起来对、但中间读了不该读的数据的 Agent，不能算通过。Agent evaluation cannot look only at the final answer. Record at least: whether the task was completed, whether the steps were reasonable, whether tool calls were correct, whether permissions were exceeded, the cost, and whether it exited safely on failure. An agent with a plausible answer that read data it should not have read has not passed.

先做固定任务集：同一批任务、同一套工具、同一环境、同一预算，重复跑。任务集要包含正常、边界、失败和恶意输入。只测顺风顺水的任务，上线后一定会在异常输入上出问题。Start with a fixed task set: same tasks, same tools, same environment, same budget, repeated. Include normal, edge, failure and adversarial inputs. Testing only happy paths guarantees trouble on abnormal inputs after launch.

上线前先影子运行：让 Agent 在真实输入上跑，但不执行副作用，只记录它会做什么。对比人工结果，统计「会做对」「会做错」「会越权」「会卡住」四类，再决定是否放权。Run in shadow mode before launch: let the agent process real inputs without side effects and record what it would do. Compare with human results across four buckets — would do right, would do wrong, would exceed permission, would get stuck — then decide how much authority to grant.

判断句：如果评测只报「成功率」，没有失败样本、越权样本和成本，它还不能支撑上线决定。Rule of thumb: if an evaluation reports only a success rate, without failure cases, permission violations and cost, it cannot support a launch decision.

7 · 失败分支：先让系统停得住7 · Failure branches: make the system able to stop

智能体的失败往往不是「答错一句」，而是「做错一件事」。失败分支要按副作用分级：只读的可以重试，写入的要先检查再补偿，不可逆的要人工介入。Agent failures are often not a wrong sentence but a wrong action. Grade failure branches by side effect: read-only can retry, writes need check-then-compensate, irreversible actions need a human.

8 · 最小落地路径8 · A minimum path to deployment

先做一条只读、单任务、可回放的流程；跑稳后再逐个加工具、加写权限、加自动化。每加一个能力，都要重新跑同一套任务集。Start with one read-only, single-task, replayable process. After it is stable, add tools, write permissions and automation one at a time. Every added capability must rerun the same task set.

  • 写清任务、输入、输出、完成标准和不可逆动作。Write the task, input, output, done criteria and irreversible actions.
  • 只接一个必要工具，定义参数、返回、失败和幂等性。Connect one necessary tool; define arguments, returns, failures and idempotency.
  • 用运行时强制权限，不把权限写进提示词。Enforce permissions in the runtime, not in the prompt.
  • 记录每一步，先做到可回放。Record every step; make replay possible first.
  • 加步数、时长、成本、重试四道闸。Add four gates: steps, duration, cost, retries.
  • 用固定任务集测正常、边界、失败和恶意输入。Test normal, edge, failure and adversarial inputs on a fixed task set.
  • 影子运行，对比人工结果与越权率。Run in shadow mode; compare with human results and permission-violation rate.
  • 小范围放权，保留人工审批与一键停。Grant authority gradually; keep human approval and a stop button.
四个常见误区：Agent 越多越好；自主等于不用审批；记忆就是向量数据库；演示能跑就等于能上线。Four common mistakes: more agents are better; autonomy means no approval; memory means a vector database; a working demo means ready to ship.
